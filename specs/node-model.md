# Node Model - nodes / clusters / dimensions (v0.1)

> Purpose: a knowledge-structure layer on top of the Document API (content ->
> pages) that powers the opt-in **node mode**. It does not replace the
> intuitive-mode organization of content.
> Implementation: `scripts/extract-nodes.mjs`,
> `site/.vitepress/theme/nodes.spec.json` (generated), future `NodeView`.

## 1. Core concepts

### 1.1 Node - the minimal knowledge unit
- Examples: a word (`get`), a theorem (`Pythagorean theorem`), a fact.
- **Context deltas**: the same concept differs slightly across contexts, so a
  node definition is not one string but:

```
Node := { id, kind, name,
          definition: { base, deltas: [{ context, change }] },
          edges: [{ to, kind }],        // relations to other nodes (directed or not)
          labels: { <dimension>: [tag...] } }
```

- **Fairness**: nodes are equal-weighted. The data model has **no weight field**;
  frequency/reference counts are only emergent statistics, never a weight in
  clustering or ranking.

### 1.2 Cluster - an abstraction product, not an entity
- A cluster = a **view** over annotated nodes. Grouping nodes by their labels
  on some dimension yields clusters; labels are **hierarchical**, so clusters
  can contain clusters (word -> part-of-speech -> vocabulary).
- Example (English vocabulary): `get/make/take` share `verb` on the **pos**
  dimension but may sit in different themed clusters on the **topic** dimension.
  "Same cluster" only makes sense given the active dimension.
- Consequence: **only nodes and their labels are stored - never cluster
  definitions.** Clusters emerge at runtime (emergence); switching dimensions
  re-renders instantly.

### 1.3 Dimension - an abstraction axis (non-unique)
- The same set of nodes has many legitimate clusterings (by pos, by topic, by
  first letter, by frequency band...). Each clustering scheme is a dimension.
- Dimension changes obey three machine-checkable constraints:
  1. **Localization**: a label edit affects only one local neighborhood (nodes
     of one unit) at a time - no one-shot global relabeling; edits are versioned.
  2. **Gradual increase**: within an existing dimension, parent labels may only
     be refined into children - never crudely replaced. A wholly new clustering
     must be declared as a **new dimension**, not a mutation of an old one.
  3. **Smooth edges**: two adjacent nodes (sharing an example/co-occurrence/
     paragraph) that land in different clusters must share an ancestor cluster
     on some lower level. Check rule:
     `adjacent && no common ancestor cluster -> warn about a candidate bridge`.

## 2. Two modes

| | intuitive mode (current) | node mode (opt-in) |
|---|---|---|
| view | author: course -> unit (linear tree) | learner: nodes & clusters |
| content files | unchanged | unchanged (nodes are an overlay) |
| when | default | after explicitly enabling the unit/course |
| ideas | - | localization, emergence, fairness |

Enable per unit: frontmatter `nodeMode: true` (optionally `nodeDims`),
or globally per course via courses.config.json `nodeModeDefault`.

## 3. External API (optional Document-API additions)

```yaml
---
id: e-vocab-001
nodeMode: true          # optional: enable the node view on this unit
nodePrompt: xxx.prompt.md  # optional: consistency guidance for node-ification
nodeDims: ["pos", "topic"] # optional: allowed dimensions (order = switch order)
---
```

- **nodePrompt semantics**: the reference used during node-ification (granularity,
  naming language, glossary, prohibitions such as "never merge get/obtain").
  Both AI and mechanical extraction must honor it.
- **No nodePrompt**: automatic mode. Priority: deterministic mechanical
  extraction (tables/definition patterns) when structure exists; otherwise an
  AI pass using the built-in default template. Every produced node carries
  `origin: mechanical | ai-auto` for auditability.
- For long-term reproducibility prefer content that is mechanically
  extractable; AI is the fallback and a polish layer.

## 4. Data & artifacts

- `site/.vitepress/theme/nodes.spec.json`: per-page node config
  (mode/prompt/dims) generated by gen-catalog; consumed by the extractor and
  the future NodeView.
- `npm run nodes`: mechanical extraction (dry prints stats and samples;
  `--write` writes `site/.vitepress/theme/nodes.gen.json`):
  `{ schemaVersion: 1, pages: [{ path, id, nodes: [{ id, name, kind, origin, labels }] }], stats }`
- Node ids: `<unitId>.<slug>` (mechanical) or explicit `[[<id>]]` references
  in content (future cross-page edges).

## 5. Mechanical extraction rules (v0.1 deterministic part)

1. **Table units** (e.g. vocabulary lists): recognize the term column
   (`word`/`term`/`单词`) and feature columns (pos/definition/topic/level).
   Each row -> a node; feature values are stored as `labels[<header>]` (the
   header name IS the dimension - dimensions emerge from the data). Dedupe
   within the page.
2. **Definition patterns**: `**term** -- gloss` / `**term**: gloss` ->
   node(kind=definition).
3. Anything else: v0.1 does not guess (noise control); only `origin: ai-auto`
   may extend.

## 6. AI hook contract (placeholder, executor in v0.2)

Input: unit body + mechanically extracted nodes + nodePrompt (if any) + dims
whitelist. Output (strict JSON):
`{ nodes: [{ name, kind, deltas?, labels }], issues: [...] }`.
Merging: mechanical results are authoritative; AI only adds
`origin=ai-auto` items; conflicts prefer mechanical and produce a diff report
(never silently overwrite).

## 7. What fairness/emergence/localization mean in the implementation

- **Emergence**: NodeView reads no cluster table - only nodes.labels + the
  active dimension, and aggregates on the fly.
- **Fairness**: nodes render with no weight differences; sorting allows only
  name/alpha or label order of the active dimension.
- **Local + gradual + smooth**: label writes accept one
  `(unitPath, dimension, nodeIds)` change at a time; the validator checks the
  three §1.3 constraints and emits a warn/error list.
